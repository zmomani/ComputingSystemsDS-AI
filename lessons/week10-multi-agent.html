"A Visual Guide to LLM Agents — Multi-Agent Systems"

Explore the fascinating world of Large Language Model Agents. Level: Intermediate · ~30 min.

This lesson follows the tutorial A Visual Guide to LLM Agents by Maarten Grootendorst — read it alongside this page for its many diagrams.

1. Introduction to LLMs

  • Traditionally, a Large Language Model does nothing more than predict the next token. By sampling many tokens in a row, the model can mimic a conversation and give longer answers.
  • Two main limitations motivate agents:
  • No memory between conversations. An LLM does not remember what was said earlier; a follow-up question cannot be connected to the previous exchange.
  • Weak basic arithmetic. LLMs often fail at basic multiplication and division.
  • This does not make LLMs bad. They do not need to do everything, because external tools, memory, and retrieval systems can compensate for these gaps.

2. Augmented LLMs & Agents

  • Anthropic calls an LLM extended with external systems (tools, memory, retrieval) an Augmented LLM. For example, the model can call a calculator rather than do multiplication itself.
  • This lesson uses the Russell & Norvig definition (AI: A Modern Approach, 2016): an agent is anything that can be viewed as perceiving its environment through sensors and acting upon that environment through actuators.
Component Description
Environment The world the agent interacts with
Sensors Used to observe the environment
Actuators Tools used to interact with the environment
Effectors The "brain" or rules that decide how to go from observations to actions
  • Because LLMs are textual models, an LLM agent observes the environment through textual input and acts through tools (e.g. searching the web). The Augmented LLM is a generalization of this framework: the LLM handles understanding and planning, tools handle actions, and memory tracks what has been done (figures: "Agent Framework", "Augmented LLM Framework", "Agent Components").
  • Autonomy levels. Agents vary in their degree of autonomy. The more the LLM decides how the system behaves, the more "agentic" the system is. Tool use can follow a fixed order set by the framework, or the LLM can choose which tool to use and when.

3. Memory Systems

  • Core problem: LLMs are forgetful; more precisely, they perform no memorization between interactions.

Short-term memory (working memory)

  • A buffer for the (near-)immediate context, including the agent's recent actions.
  • The most straightforward implementation is the context window — the number of tokens the LLM can process. The LLM is effectively told what the conversation was rather than memorizing it (figures: "Context Window", "Context Window Memory").
  • Summarization: for smaller context windows or large histories, another LLM summarizes the conversation so far.

Long-term memory

  • Covers dozens or hundreds of steps the agent may need to retain.
  • Common technique: store all previous interactions, actions, and conversations in an external vector database; retrieve relevant pieces when needed. This is Retrieval-Augmented Generation (RAG) (figures: "Vector Database Creation", "Vector Database Retrieval").

Memory types (CoALA)

The paper Cognitive Architectures for Language Agents (CoALA) couples four psychological memory types — working, episodic, semantic and procedural — to LLM agents. Two of them matter most here:

Memory type Definition
Semantic Facts about the world
Working Current and recent circumstances

Different information can live in different stores — e.g. semantic memory kept separate from working memory — which helps when designing agent frameworks.

4. Tools & Interaction

  • Tools let an LLM interact with an external environment (a database) or run external applications (custom code). Two categories:
  • Fetching data — retrieve up-to-date information.
  • Taking action — e.g. scheduling a meeting or ordering food.
  • To use a tool, the LLM generates text matching the tool's API, usually JSON, so a code interpreter can execute it. Illustrative shape of such a call:
{"name": "multiply", "arguments": {"a": 123, "b": 456}}
  • Function calling: developers define custom functions (e.g. a basic multiplication function) that the LLM can call with parameters. Most current LLMs can perform tool use; some need careful prompting.
  • Fixed tool order: the agentic framework predefines the order of tool use. Autonomous tool selection: the LLM decides which tool to use and when. Agents are essentially sequences of LLM calls with autonomous selection of actions and tools.
  • Research moved from prompting for tool use to training for it:
  • Toolformer — one of the first approaches to train a model to decide which APIs to call and how (three-step figure series).
  • ToolLLM — LLMs using thousands of tools.
  • Gorilla — LLMs easily retrieving the most relevant tools.
  • Model Context Protocol (MCP): Anthropic developed MCP to make tools easier to implement across agentic frameworks; it standardizes API access for services such as weather apps and GitHub. See Week 11.

5. Planning & Reasoning

  • Planning breaks a task into actionable steps and lets the model reflect iteratively on past behavior, updating the plan when necessary.
  • Planning requires complex reasoning; the LLM should show this reasoning before taking the next step. Reasoning is enabled by fine-tuning or by prompt engineering:
  • Chain-of-Thought prompting — provide examples of step-by-step reasoning so the model explains its thinking before answering.
  • Zero-shot Chain-of-Thought — add the phrase "Let's think step-by-step" without examples.

ReAct (Reason and Act)

Achieved through prompt engineering rather than training. The prompt describes three steps:

Step Description
Thought A reasoning step about the current situation
Action A set of actions to execute (e.g., tools)
Observation A reasoning step about the result of the action

The cycle Thought → Action → Observation repeats until an action specifies that the result should be returned. By iterating, the LLM can plan actions, observe their output, and adjust.

Reflexion

  • Adds what ReAct lacks: reflection on failure. Uses verbal reinforcement so agents learn from prior failures.
  • Memory modules track actions (short-term) and self-reflections (long-term); together they help the agent identify improved actions.

SELF-REFINE

  • A loop in which refining the output and generating feedback are repeated.

6. Multi-Agent Systems

Why one agent is not enough

  • Too many tools complicate tool selection.
  • Context becomes too complex.
  • The task may require specialization.

Structure

  • Multi-agent systems are frameworks in which multiple agents — each with tools, memory, and planning — interact with each other and with their environments.
  • Typically specialized agents, each with its own toolset, overseen by a supervisor that manages communication and assigns tasks (figures: "Multi-Agent System", "Multi-Agent Architecture").
  • Two core design components:
  • Agent initialization — how individual specialized agents are created.
  • Agent orchestration — how all agents are coordinated.

Generative Agents

Generative Agents: Interactive Simulacra of Human Behavior (Park et al.) created software agents that simulate believable human behavior. The Memory module is the most vital component; it stores planning and reflection behaviors and all events so far.

Components common to multi-agent frameworks: Profile, Perception of the environment, Memory, Planning, Available actions.

Frameworks

Framework Notes
AutoGen Collaborative; inter-agent communication differs from the others
MetaGPT Collaborative; inter-agent communication differs from the others
CAMEL Role-playing: the user defines an AI User (represents the human and guides the process) and an AI Assistant; the two collaborate by interacting with each other to resolve the query

The growth of these frameworks has been explosive.

7. Conclusion

LLM Agents combine the language understanding of LLMs with the ability to interact with an environment through tools, keep information in memory, and plan complex actions. Areas of ongoing progress:

  • More advanced planning and reasoning
  • Better memory systems for context retention
  • Improved tool integration and execution
  • Stronger coordination among multiple agents
  • Self-reflection and self-improvement mechanisms

"Agent-to-Agent Protocols: A2A and MCP"

Standardizing communication between AI agents and data sources. Level: Intermediate · AI Agents · ~25 min.

Google's Agent2Agent (A2A) protocol and Anthropic's Model Context Protocol (MCP) are two complementary protocols that are changing how AI systems interact.

A2A (Agent2Agent Protocol)

A2A is an open protocol announced by Google in April 2025. It is designed to let AI agents communicate and interoperate regardless of the framework or vendor they are built on. More than 50 technology and service partners support it, including Atlassian, Box, Cohere, Intuit, LangChain, MongoDB, PayPal, Salesforce, SAP, and ServiceNow.

Design principles

  • Embrace agentic capabilities — supports natural, collaborative workflows between agents.
  • Build on existing standards — HTTP, SSE (Server-Sent Events), and JSON-RPC.
  • Secure by default — enterprise-grade authentication and authorization.
  • Support long-running tasks — real-time feedback and state updates.
  • Modality agnostic — multiple content formats, including audio and video.

Key components

  • Agent Card — a public metadata file (JSON, served at /.well-known/agent-card.json) describing an agent's capabilities, skills, endpoint URL, and authentication requirements. Clients use it for discovery.
  • Task-oriented communication — work is organized as tasks with a defined lifecycle. A task may complete immediately or remain active for an extended period.
  • Messages, Parts, Artifacts — agents exchange messages whose content is carried as parts (text, files, or structured data); a finished task may return artifacts.
  • UX / capability negotiation — agents negotiate the right content format, explicitly including user-interface capabilities.

Agent Card fields (from the sample)

Field Meaning
protocolVersion A2A protocol version the agent speaks
name, description, version Display name, what the agent does, version string
url, preferredTransport The agent's A2A endpoint and its transport (JSONRPC, GRPC or HTTP+JSON)
securitySchemes Named auth schemes (sample: an oauth2 authorization-code flow with authorizationUrl, tokenUrl and scopes)
security Which scheme(s) and scopes a client must present
capabilities.streaming Whether SSE streaming is supported
capabilities.pushNotifications Whether the agent can push task updates to a client webhook
defaultInputModes, defaultOutputModes Media types the agent accepts and produces (e.g. text/plain, application/json)
skills[] Each with id, name, description, tags, optional examples, inputModes, outputModes

A2A workflow (step by step)

  1. Agent Discovery — the client agent reads the remote agent's Agent Card to learn its capabilities and endpoints.
  2. Task Initialization — the client sends a task request with an initial message and task parameters.
  3. Task Processing — the remote agent completes the task immediately or enters a working state for longer operations.
  4. Status Updates — for long-running tasks, the remote agent streams status updates over SSE.
  5. Message Exchange — agents exchange text, files, or structured data as parts to collaborate.
  6. Task Completion — the task reaches a terminal state (completed, failed, canceled, or rejected) and may return artifacts. Along the way it may pause in input-required or auth-required until the client responds.

A2A scenarios

Candidate sourcing — a recruiting manager needs candidates for a software engineering position. 1. The manager's agent connects to specialized recruiting agents. 2. Each agent handles one part: sourcing, screening, or scheduling. 3. The agents collaborate over A2A to find suitable candidates. 4. The manager receives a unified view of the results. 5. After selection, the manager's agent uses A2A to coordinate interview scheduling.

Multi-agent research — a data scientist needs comprehensive research on a complex topic. 1. The primary agent divides the research tasks among specialized agents. 2. A market-research agent gathers industry trends. 3. A data-analysis agent processes relevant statistics. 4. A visualization agent creates charts from the processed data. 5. The primary agent synthesizes everything into a cohesive report.

MCP (Model Context Protocol)

MCP is an open standard from Anthropic (announced November 2024) that standardizes how AI applications connect to external tools, data sources, and systems, so assistants can reach data where it lives and reduce information silos. (Full treatment in Week 11.)

Architecture

  • Host — an application such as Claude Desktop or an IDE that wants data through MCP; the entry point for user interaction.
  • Client — maintains a 1:1 connection with each server and manages protocol details.
  • Server — a lightweight program exposing specific capabilities and connecting to the underlying data sources and tools.

Key characteristics

  • Secure — operates within your security boundaries.
  • Open — community-driven, open-source standard.
  • Interoperable — works across LLM providers.
  • Extensible — adaptable to various data sources.

MCP workflow

  1. Connection Initialization — the MCP client in the host connects to a server and exchanges capabilities and protocol versions.
  2. User Query — the user interacts with the host; the model identifies a need for external data.
  3. Resource Request — the client requests the needed data or tool from the appropriate server.
  4. Server Processing — the server accesses the resource (file, database, API) and formats the data.
  5. Response Delivery — the server returns the formatted data to the client via the standard protocol.
  6. AI Response Generation — the model uses the retrieved data to produce a more informed response.

How A2A and MCP complement each other

  • MCP connects AI models to the tools, data, and systems they need — "the protocol to connect agents with their structured tools."
  • A2A lets end-users or other agents work with specialized agents (one that finds job candidates, one that summarizes meeting notes) and lets those agents collaborate.

Writer-Critic loop: the evaluator-optimizer pattern (pure Python)
def writer(topic, notes=None):
    draft = f"{topic} replaces the feed-forward layer with several experts."
    if notes:
        draft += " A router picks the top-2 experts per token (Shazeer et al., 2017)."
    return draft

def critic(draft):
    score = 5 + 3 * ("(" in draft) + 2 * ("router" in draft)
    notes = [] if score >= 8 else ["add how routing works", "cite a source"]
    return score, notes

topic, notes = "Mixture of Experts", None
for round_ in range(1, 4):
    draft = writer(topic, notes)
    score, notes = critic(draft)
    print(f"round {round_}: score {score}/10  notes={notes}\n  {draft}")
    if score >= 8:
        print("accepted")
        break

# 1. Minimal ReAct loop with a toy tool set (no API key needed: a scripted "LLM")
import re, json

TOOLS = {
    "multiply": lambda a, b: a * b,
    "search": lambda q: f"Stub result for '{q}'",
}

def fake_llm(trace):
    # A scripted policy standing in for the model; replace with a real LLM call.
    if "Observation" not in trace:
        return 'Thought: I need 17*23.\nAction: {"name":"multiply","arguments":{"a":17,"b":23}}'
    return "Thought: I have the answer.\nFinal Answer: 391"

trace = "Question: What is 17 times 23?"
for step in range(5):
    out = fake_llm(trace)
    trace += "\n" + out
    if "Final Answer:" in out:
        break
    call = json.loads(re.search(r"Action: (\{.*\})", out).group(1))
    obs = TOOLS[call["name"]](**call["arguments"])
    trace += f"\nObservation: {obs}"
print(trace)
Short-term memory: a fixed-size context window with summarization fallback
# 2. Short-term memory: a fixed-size context window with summarization fallback
from collections import deque

WINDOW = 6  # tokens for illustration
history = deque(maxlen=WINDOW)
summary = ""

def add_turn(text):
    global summary
    for tok in text.split():
        if len(history) == WINDOW:
            summary = (summary + " " + history[0])[-40:]  # crude "summarizer"
        history.append(tok)

for turn in ["my name is Zaid", "I teach big data", "what is my name"]:
    add_turn(turn)
print("window :", list(history))
print("summary:", summary.strip())
Long-term memory via RAG with a tiny vector store (numpy only)
# 3. Long-term memory via RAG with a tiny vector store (numpy only)
import numpy as np

docs = ["The meeting is on Tuesday at 10am.",
        "The project deadline is 30 November.",
        "Zaid prefers Python for data science labs."]

def embed(text):  # bag-of-characters embedding, enough to demonstrate retrieval
    v = np.zeros(128)
    for ch in text.lower():
        v[ord(ch) % 128] += 1
    return v / (np.linalg.norm(v) + 1e-9)

store = np.stack([embed(d) for d in docs])
query = "when is the deadline?"
scores = store @ embed(query)
print("retrieved:", docs[int(scores.argmax())])
Supervisor routing in a multi-agent system
# 4. Supervisor routing in a multi-agent system
import re

AGENTS = {
    "math":   lambda task: f"[math agent] {eval(task)}",
    "writer": lambda task: f"[writer agent] Draft: {task.title()}",
}

def supervisor(task):
    # route to the math agent only if the whole task is an arithmetic expression
    is_math = re.fullmatch(r"[\d\s+\-*/().]+", task) is not None
    return AGENTS["math" if is_math else "writer"](task)

for t in ["12*12", "introduce multi-agent systems"]:
    print(supervisor(t))

Task lifecycle state machine
# 2. Task lifecycle state machine
TRANSITIONS = {
    "submitted": {"working", "auth-required", "rejected", "canceled"},
    "working": {"input-required", "auth-required", "completed", "failed", "canceled"},
    "input-required": {"working", "canceled"},   # interrupted: waiting on the client
    "auth-required": {"working", "canceled"},    # interrupted: waiting on credentials
}
TERMINAL = {"completed", "failed", "canceled", "rejected"}

class Task:
    def __init__(self):
        self.state = "submitted"
        self.history = [self.state]
    def move(self, new):
        if self.state in TERMINAL or new not in TRANSITIONS[self.state]:
            raise ValueError(f"illegal {self.state} -> {new}")
        self.state = new
        self.history.append(new)

t = Task()
for s in ["working", "input-required", "working", "completed"]:
    t.move(s)
print(" -> ".join(t.history))

# 3. Build a JSON-RPC 2.0 'message/send' request with a multi-part message
import json, uuid

def message_send(text, data):
    return {
        "jsonrpc": "2.0",
        "id": str(uuid.uuid4()),
        "method": "message/send",
        "params": {
            "message": {
                "messageId": str(uuid.uuid4()),
                "role": "user",
                "parts": [
                    {"kind": "text", "text": text},
                    {"kind": "data", "data": data},
                ],
            },
        },
    }

print(json.dumps(message_send("Find Python developers in Amman",
                            {"jobTitle": "Data Engineer", "skills": ["Python", "Spark"]}),
                 indent=2))

# 4. Simulate SSE status updates from a long-running remote agent
import json, time

def remote_agent_stream():
    for i, state in enumerate(["working", "working", "working", "completed"]):
        time.sleep(0.2)
        event = {"kind": "status-update", "taskId": "task-1", "contextId": "ctx-1",
                 "status": {"state": state}, "final": state == "completed"}
        # each SSE chunk carries one JSON-RPC response whose result is a TaskStatusUpdateEvent
        yield "data: " + json.dumps({"jsonrpc": "2.0", "id": 1, "result": event}) + "\n\n"

for chunk in remote_agent_stream():
    print(chunk, end="")
